DEPLOYMENT OPTIONS DISCUSSED

Recommended simplest architecture for this existing code:
- Deploy React assets and the PHP/LavaLust app together as one PHP web service (Docker is a possible Render route).
- Use a separately hosted, persistent MySQL database and set DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME in the service environment.
- Keeping frontend and API on one domain preserves the current same-origin /api/v1 behavior and avoids the extra complexity of cross-origin login cookies and CSRF.
- Render supports Docker/PHP deployment, but its managed database offering is PostgreSQL, not a drop-in replacement for this MySQL app. Do not connect this MySQL-configured app to Render Postgres without a planned backend/schema migration.
- Render free web services can sleep after inactivity; this can make the first visit/message after idle noticeably slow. Free service/storage limitations must be checked at deployment time. A free database plan may have expiry/data-persistence limits; don't use it for important production data.

Alternative discussed:
- Deploy the Vite/React frontend on Vercel and host PHP plus MySQL elsewhere.
- This is possible but is not currently plug-and-play: the React code calls same-origin /api/v1 and PHP serves the built Vite assets. Separate hosting requires an API base URL, CORS/credentials rules, secure cross-site cookie and CSRF design, and SPA route fallbacks. Prefer same-site custom subdomains if feasible.
- Vercel frontend hosting does not host this existing PHP/LavaLust/MySQL backend automatically.

- Don't promise or configure "free production hosting" until current host/database quotas and persistence rules are checked. Free tiers are suitable for demos, with limitations.
